Frequently asked questions

Everything you wanted to know about quantization, benchmarks, and how to read the results.

Quantization & GGUF

What is quantization?

Quantization reduces the numerical precision of a language model's weights. A FP16 model uses 2 bytes per weight; a Q4 model uses roughly 0.5 — a 4× reduction in memory footprint.

The trade-off is rounding error that slightly degrades model quality. This site measures exactly that cost across several academic benchmarks.

What is the GGUF format?

GGUF (GPT-Generated Unified Format) is the file format used by llama.cpp. It bundles quantized weights, tokenizer config, and model metadata into a single file.

It is now the de facto standard for running quantized LLMs locally, on consumer CPUs and GPUs.

What is the difference between IQ and Q quantization levels?

Q levels (e.g. Q4_K_M) use uniform block quantization developed by the llama.cpp team.

IQ levels (e.g. IQ2_M) or UD-IQ use importance-aware (or "Unsloth Dynamic") quantization: layers that matter most to model quality are quantized less aggressively, preserving accuracy at the same file size.

As a rule of thumb, IQ formats outperform classic Q formats at the same file size — especially at very low bit depths (1–2 bits).

What is the difference between Dense and MoE architectures?

A Dense model activates all its parameters at every inference step. A MoE (Mixture of Experts) model only activates a subset of its parameters (the "experts") per token.

In practice, a 35B MoE model may activate only 3B parameters per token — offering inference speed close to a 3B Dense model while retaining quality closer to a 35B.

The Dense vs MoE section on the main site compares these architectures head-to-head across all benchmarks.

Benchmarks & results

Why these specific benchmarks?

The current suite uses BigCodeBench and BBEH-mini, chosen for complementary coverage and resistance to saturation:

BigCodeBench — diverse code generation across real-world libraries; much harder than HumanEval and less prone to ceiling effects on capable models.
BBEH-mini — a broad mix of hard reasoning tasks (logic, math, language understanding) that remains discriminative even on strong models.

Earlier benchmarks (ARC-Challenge, IFEval, GSM8K, HumanEval) were dropped because they saturate on current models — scores cluster so close to the ceiling that no meaningful conclusion can be drawn about quantization impact.

IFEval will be re-introduced later using a different harness to keep results comparable across runs. SWE-bench is also planned, subject to hardware availability.

How do I read the charts?

The horizontal axis represents the quantization level, from most compressed (left) to least compressed (right). The vertical axis shows the benchmark score as a percentage.

A steep drop towards the left means the model handles aggressive quantization poorly. A flat line indicates strong resilience.

The table below each chart shows exact scores and the GGUF file size fetched from Hugging Face at build time.

What hardware was used?

Benchmarks are run with Inspect AI (UK AISI) as the evaluation harness, using llama-server from llama.cpp as the inference backend.

A single RTX 3060 12 GB consumer GPU is used — no cloud, no H100. Context is capped at 64k tokens, which means results are not directly comparable to official leaderboard scores measured without such constraints.

See the Methodology section on the main site for full details.

Are the results reproducible?

Yes. All raw result files are available in the yrougy/llm-quant-bench GitHub repository. The exact commands used for each evaluation are documented in the README.

Minor variations may occur depending on the llama.cpp version and sampling parameters used.

Contributing & updates

How can I contribute?

Contributions are welcome via the GitHub repository: yrougy/llm-quant-bench.

You can propose new models to benchmark, result corrections, methodology improvements, or contributions to the site generator code.

How often are results updated?

Results are added manually as evaluations are completed. There is no fixed schedule — updates happen when notable new models or quantization variants are released.

The date of the latest update is visible in the GitHub commit history.
